## Objective

Allow the oracle to steer clustering along a specific semantic axis
(e.g. "angry tone", "battery life") at any moment of the session, instead of
always starting from a generic k-means on the topic.

---

## Feature architecture (current state)

### Entry point: `semantic_reembed` operation emitted by the LLM

In the current version (after the integration of Davide's commit `d0480c7`),
`axis_hint` **is no longer a field of the `InputOracle` schema**. The re-embedding
is now an operation like any other: the oracle writes in free language and
`f_output` decides to emit `{"type": "semantic_reembed", "axis_label": "..."}`.

It can happen **at any turn**, not only the first one.

### Full flow

```
POST /turns  (oracle free-text input)
    │
    ├── clarify-confirmation short-circuit (deterministic)
    │   If the previous turn had a clarify_pending AND the oracle confirms
    │   with "yes"/"sì"/"ok"/etc. → bypass f_output, emit semantic_reembed
    │   directly with the saved axis
    │
    └── f_output (LLM) → classifies the intent
            │
            ├── action:"clarify"  (bare ambiguous phrase: "angry tone", "battery life")
            │   → save {"type":"clarify_pending","axis_label":"..."} in state_snapshot
            │   → show confirmation question to the oracle
            │
            ├── action:"semantic_reembed"  (explicit intent: "cluster by X")
            │   → _run_semantic_reembed(axis_label)
            │       → semantic_clustering → new clusters + SoftAssignment
            │
            └── merge / split / rename / move / no_change / explain
                    → f_apply_operations → cluster_operations
```

### Semantic axis detection in subsequent turns

Once a session has performed a semantic_reembed, the axis is retrieved
from the turn history instead of being re-executed:

```python
# turns.py
session_axis_hint = _active_axis_from_history(prior_turns)
# scans turns backwards looking for the last semantic_reembed op
# accepts both "axis_label" (new) and "axis_hint" (backward compatibility for old sessions)
```

It is passed to `f_apply_operations → merge/split_cluster → name_clusters` so
the names of clusters generated by structural operations remain coherent with the axis.

## Implementation detail

### `f_semantic_reembed.py`

Two strategies + hybrid selector:

```
_generate_axis_poles(axis_label)
  → (pole_pos_text, pole_neg_text)   # 1 LLM call, always

_cosine_axis_scores(points, pole_pos_text, pole_neg_text)
  → cosine_var > COSINE_VARIANCE_THRESHOLD (0.01)?
      yes → use cosine scores directly
      no  → _llm_axis_scores(points, axis_label)
              → llm_std < LLM_STD_THRESHOLD (1.0)?
                  yes → raise AxisNotDiscriminativeError
                  no  → use LLM scores
```

**LLM pole generation (`_generate_axis_poles`)**

Asks the LLM for two concrete texts as poles (not abstract phrases like "very angry").
Concrete texts will embed better because they live in the same distribution
as the data. Automatic fallback to abstract phrases in case of error.

**Cosine strategy (free)**

```python
score(p) = dot(emb_p_norm, pole_pos) - dot(emb_p_norm, pole_neg)
```

Works when `cosine_variance > COSINE_VARIANCE_THRESHOLD`.

**LLM batch scoring strategy (fallback)**

LLM scores each text from 0 to 10 along the axis (batches of 25).
For large datasets (N > `LLM_SAMPLE_SIZE = 200`): samples 200 points and has them
scored, then propagates the scores to the others via **cosine nearest-neighbour**
on the original embedding. Reduces from ~48 to ~8 LLM calls on a 1200-point dataset.

### Experiment: Ridge vs NN, N=200 and N=600 (concluded)

**Initial hypothesis:** Ridge regression on the MiniLM subspace finds a linear
direction that correlates with tone better than nearest-neighbour, which propagates by topic.

| Session | N | Method | std (final) | R² | Silhouette | min/max | Balance |
|---------|---|--------|-------------|----|------------|---------|---------|
| 1 | 200 | Ridge α=1.0 | 1.507 | 0.525 | 0.340 | in range | — |
| 2 | 200 | Ridge α=0.01 | 4.087 | 0.990 | 0.357 | -11.5..18.0 | — |
| 3 | 200 | NN | ~2.8 | — | ~0.55 | 0..10 | — |
| 4 | 600 | Ridge α=1.0 | 2.37 | 0.330 | 0.489 | -2.1..10.0 | 993/207 |
| **5** | **600** | **NN** | **3.171** | **—** | **0.538** | **0..10** | **855/345** |

**N=200 analysis:**
- Ridge α=1.0: D=384 >> N=200 → strong regularization crushes std to 1.5, silhouette 0.340
- Ridge α=0.01: massive overfitting (R²=0.990), extrapolation -11.5..18.0, silhouette 0.357
- NN: bimodality preserved (extremes 0 and 10), silhouette ~0.55 — baseline

**N=600 analysis:**
- Ridge α=1.0: R² drops to 0.330 (less overfitting, D~N regime), range almost in bounds (-2.1..10.0),
  but compressed std (2.37) and imbalanced clusters (993/207) → silhouette 0.489 < NN
- NN: std 3.171 (greater coverage → closer neighbours), perfect range 0..10,
  more balanced clusters (855/345), silhouette 0.538

**Conclusion:**
Ridge does not outperform NN on any relevant metric even at N=600.
The theoretical advantage (linear tone direction) does not translate into better
separation: Ridge smooths the distribution (gaussian) where NN is strong (bimodality).

N=600 with NN gave silhouette 0.538 vs ~0.55 at N=200 — improvement within
the noise of pole generation, not reliable. Latency instead triples
(24 LLM calls vs 8, ~48s vs ~16s just for scoring). Final configuration:
**NN with N=200** (commit `044423a`) — acceptable latency for an interactive system.

**`AxisNotDiscriminativeError`**

Raised when `llm_std < LLM_STD_THRESHOLD`. `turns.py` catches it and
returns an ask-turn without advancing `turn_number` — the DB is not touched.

**Resulting hybrid matrix**

```
X = [ orig_norm × sqrt(1 - axis_weight) | axis_norm × sqrt(axis_weight) ]
shape: (N, D+1)   dtype: float32
```

`axis_weight=0.7` → 70% axis, 30% topic. The `sqrt` scaling ensures that
`axis_weight` is the exact fraction of k-means signal coming from the axis
(geometric reasoning: expected squared distance ≈ 2 for both components).

### `semantic_clustering.py`

```python
K_AUTO_MIN = 2
K_AUTO_MAX = 5
```

k is chosen automatically via silhouette score (`_auto_select_k`) when not
passed explicitly. It tests k=2..5 on the already-computed new hybrid space and
returns the k with the highest average silhouette. Replaces the old fixed cap
`AXIS_K_CAP = 3`.

Flow:
```
reembed_for_axis(points, axis_hint, axis_weight)
  → X (hybrid matrix)
  → _auto_select_k(X, K_AUTO_MIN, K_AUTO_MAX)
  → KMeans(k) on X
  → dissolve old clusters (dissolved_at_turn = turn_number)
  → create new DbCluster
  → name_clusters(axis_hint=axis_hint)
  → write SoftAssignment at turn_number
```

### `turns.py` — refactor of the semantic path (rev 10)

**Differences vs rev 9:**

| Aspect | Rev 9 | Rev 10 |
|--------|-------|--------|
| Trigger | `axis_hint` in payload (Turn 1 only) | `semantic_reembed` operation emitted by f_output (any turn) |
| Schema | `InputOracle.axis_hint: Optional[str]` | Field removed |
| Axis detection in later turns | `prior_turns[0].oracle_input.get("axis_hint")` | `_active_axis_from_history(prior_turns)` scans ops |
| Ambiguous intent ("angry tone") | Silent `no_change` | `clarify` with question + `clarify_pending` in state_snapshot |
| Confirmation ("yes") | LLM had to infer the axis from history | Deterministic: `_pending_clarify_axis` + `_is_affirmation` |

**New helper `_active_axis_from_history`:**

Searches previous turns (backwards) for the last `op.type == "semantic_reembed"`
and returns its `axis_label`. Also accepts `axis_hint` for backward compatibility.

**New helper `_run_semantic_reembed`:**

Extracts the loading of `DataPoint`s from the DB and the call to `semantic_clustering`
into a separate reusable function.

**Deterministic flow for confirmation:**

```python
# 1. At the start of create_turn:
pending_axis = _pending_clarify_axis(prior_turns)
if pending_axis and _is_affirmation(payload.raw_text):
    # bypass f_output, builds raw directly
    raw = {"action": "semantic_reembed",
           "operations": [{"type": "semantic_reembed", "axis_label": pending_axis}], ...}

# 2. After f_output, if action=="clarify":
pending_label = raw.get("axis_label")
snapshot_operations = [{"type": "clarify_pending", "axis_label": pending_label}]
operations = []  # no changes to clustering this turn

# 3. End of turn — state_snapshot uses snapshot_operations if present:
ops_to_store = snapshot_operations if snapshot_operations else operations
```

### `f_output.txt` — new instructions for semantic intent

Added `clarify` as a new action. Three-case rule:

**(1) Explicit intent → `semantic_reembed` directly**
Phrases with an operative verb: "cluster by X", "raggruppa per X", "look at this through X",
"split everything by X", "re-cluster by X", etc.

**(2) Ambiguous intent → `clarify`**
Bare phrase without operative verb and without reference to specific clusters:
"angry tone", "battery life", "sentiment", "tono arrabbiato".
The `display` asks: "Did you mean to reorganise all clusters along the '[X]' axis?
This will dissolve the current clusters and create new ones. Reply 'yes' or
'cluster by [X]' to confirm."
The JSON also includes `axis_label: "[X]"` at the top level to allow `turns.py`
to save it without having to parse the display text.

**(3) Confirmation after clarify → `semantic_reembed` directly**
(Prompt rule, but in practice bypassed by the LLM via the deterministic mechanism
in `turns.py` described above.)

**`semantic_reembed` operation in JSON:**
```json
{"type": "semantic_reembed", "axis_label": "angry tone"}
```
Exclusive: cannot be combined with merge/split/rename in the same turn.

### Naming with axis context

When `axis_hint` is present, `name_clusters` injects the AXIS CONTEXT block into
the prompt with a **bifurcated** rule (rev 9 fix):

```
- If the texts concern '{axis_hint}' → name by position on the axis
  (e.g. 'Poor Battery Life', 'Excellent Battery Life')
- If the texts do NOT concern '{axis_hint}' → descriptive thematic name
  (e.g. 'Shipping and Returns', 'Product Durability')
```

Before the fix, the prompt explicitly forbade thematic names — causing
wrong names ("High Battery Life") on clusters whose content was unrelated to the axis.

---

### Arithmetic constraints in `f_output.txt`

The prompt explicitly covers the two cases of cluster count modification:

```
CLUSTER COUNT ARITHMETIC:
- K > N (increase): NEVER merge; emit (K-N) splits on different clusters
- K < N (decrease): NEVER split; emit ONE SINGLE merge of (N-K+1) cluster IDs
- CRITICAL: do not do "consolidate everything then expand" — go directly to splits
```

## Bibliographic reflection and future perspectives

### Limits of the hybrid MiniLM + LLM fallback approach

The current semantic reembedding architecture builds a hybrid vector
`(N, D+1)` where D=384 dimensions come from MiniLM and 1 dimension comes from the
axis score (cosine or LLM). This creates a structural asymmetry: clustering
works on 384 topical dimensions + 1 semantic dimension, which
means the semantic axis has limited influence even when `axis_weight`
is high, because the overall geometry of the space remains dominated by the
topical structure of MiniLM.

The LLM fallback frequently fails (cosine variance < 0.01) on subtle
semantic axes — sentiment, formality, tone — because MiniLM (22M parameters)
has not learned to separate these dimensions in its 384-dimensional
representation. This is not a problem solvable with more data: it is an architectural
capacity limit.

An upgrade of the base embedding model (e.g. `BAAI/bge-base-en-v1.5`, 110M
parameters, 768 dimensions) would improve the quality of the cosine strategy and
reduce the frequency of the LLM fallback. We ran a quantitative test
on 20newsgroups (300 documents, 6 classes): BGE-base reaches NMI=0.77 vs
MiniLM=0.64 (+20%) and ARI=0.75 vs 0.61 (+24%). The change was not applied
because of the computational cost on CPU (8× slower at initial embedding);
the details and the decision are documented in
[embedding-model-comparison.md](embedding-model-comparison.md).

### Alternative: instruct-tuned models

Both Fischer & Biemann (2026) — *Perspectives* — and Su et al. (2023) —
*One Embedder, Any Task: Instruction-Finetuned Text Embeddings* — use
**instruct-tuned** embedding models (e.g. `multilingual-e5-large-instruct`) that
accept an instruction as a prefix and produce embeddings oriented toward that
specific dimension.

The difference with the current approach is fundamental:

- **Current LLM fallback**: the LLM reads each text and produces *one scalar*
  (score 0-10). That number is concatenated to the existing MiniLM embedding:
  `[384 dim MiniLM | 1 dim score]`. The semantic axis enters as a single column.
- **Instruct-tuned model**: the model receives `"Represent this text by
  sentiment: [text]"` and produces a *full vector* (e.g. 1024 dimensions)
  where the whole geometry is already oriented toward the axis. Documents semantically
  coherent with respect to the axis are already close in all dimensions, not only
  one. You don't add a dimension — you redesign the space.

In practice: the LLM fallback gives a grade to each document and uses it as a
tiebreaker. The instruct-tuned model fully reorients the distance metric.

A further practical advantage: calls to an embedding model are 10-50x
cheaper and faster than calls to a generative LLM. The current fallback
on 1200 points (sample 200, 8 batches) costs ~$0.01-0.02 and ~16 seconds;
an embedding API call on the entire dataset would cost a fraction of that.

### Implementation path

Neither GPU nor training is required: there are APIs that serve
instruct-tuned models with custom instructions (Jina `jina-embeddings-v3`, Voyage
`voyage-3-large`, Together AI with `e5-large-instruct`). The change would be
localized in `f_semantic_reembed.py`: the `reembed_for_axis` function could
accept an `embedding_backend` parameter and use the instruct-tuned model
instead of the cosine+fallback pipeline, producing a matrix `(N, D_new)` instead
of `(N, D+1)` — with the advantage that the entire space reflects the requested axis.
